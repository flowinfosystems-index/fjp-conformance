FJP Quickstart

Put judgment in front of one agent action.

Start where the risk starts: immediately before a production agent can change something that matters.

What you are connecting to.

FJP is the productization of Flow's live judgment loop. For a year, that loop has processed millions of judgments, actions and resolutions: determine what matters, resolve the action, observe the outcome, then score and re-evaluate the original call.

ObserveContext, signals, tool state.
→
JudgeWhat matters and why?
→
ActWhat should happen?
→
ResolveWhat actually happened?
For agents: the loop sits between proposed action and execution. Your application remains the enforcement point.
01Choose the action boundary

Pick one action where a wrong call has a meaningful cost. Examples: issue a refund, send an external communication, commit capital, delete a record, deploy code, approve a claim, change access, or execute a transaction.

agent reasoning ↓ proposed consequential action ↓ FJP ↓ application enforcement ↓ execution
02Get your Flow key

Production access is currently provisioned directly. Your key begins with fjp_live_.

Request access
03Send the proposed action and its decision context

The resolver needs the information that should govern the action: what the agent wants to do, the relevant state, constraints, authority, evidence and material counter-signals.

curl -X POST https://resolve.flowinfo.co/api/v1/tools/judge \ -H "Authorization: Bearer fjp_live_..." \ -H "Content-Type: application/json" \ -d '{ "context": "Agent proposes a $12,000 refund. Autonomous authority: $5,000. Manager approval: absent. Customer history: 3 prior refunds in 30 days." }'
Do not send more data just because it exists. Send the context that can materially change the action. FJP's role is to resolve importance, not reward payload size.
04Use the returned judgment as the control decision

Every response carries the observable decision chain. The application's enforcement policy decides how that directive maps to execution.

signalWhat changed or what condition is material
judgmentWhy it matters, with confidence
actionWhat should happen next
falsifierA concrete, checkable condition that would reverse the call
request_idIdentifier for the later outcome
PROCEED

Execute when the returned action supports continuation.

HOLD

Do not execute while a material condition is unresolved.

ESCALATE

Route to the person or authority required by policy.

05Report what happened

The outcome is part of the product. When the relevant result becomes observable, associate it with the original request_id.

curl -X POST https://resolve.flowinfo.co/api/v1/outcomes \ -H "Authorization: Bearer fjp_live_..." \ -H "Content-Type: application/json" \ -d '{"request_id":"req_...","outcome":"confirmed","notes":"manager approval was required and obtained"}'

That closes the loop: judgment → action → outcome → resolution. Flow's internal evaluation and calibration methods remain proprietary.

06Connect through MCP when that is easier

If your agent framework supports MCP, point it at the existing resolver endpoint. The FJP tools are exposed through standard MCP tool calls.

endpoint: https://resolve.flowinfo.co/mcp auth: Authorization: Bearer fjp_live_...

The existing tools are judge, weigh, and match. The agent can call them the same way it calls other MCP tools.

07Keep model inference on your account

Flow's commercial role is the judgment/control layer, not model resale. Customer model usage should remain on the customer's provider, cloud account, private inference stack or gateway, with those model fees billed directly to the customer.

Your models. Your billing. Flow's judgment.
08Use FJP-CONF when you need the public contract

FJP-CONF tests whether the observable record is well-formed, grounded, falsifiable and accountable. It does not inspect or reveal Flow's judgment method.

$ pip install fjp-conformance $ fjp-conform record.json --level 2
